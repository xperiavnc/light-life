# 开水响应解析与失败步骤修复（2.0.2）

## 已确认与未确认

截图说明客户端期待 `$.data` 为数组，但实际读到对象；仅凭截图不能确认
实际业务码、原始消息或具体接口。开水首先读取 SKU，因此它是主要排查点。
本地官方 Java 中 `ApiService.skus` 返回原始 `JsonObject`，
`LockingAct.createObserver$lambda$6$lambda$5` 先检查 `code == 0`，
随后才将 `data` 按 `List<Sku>` 读取。没有证据支持单 SKU 对象或 `skuList` 包装。

## 修改

- 只对 `DeviceApi` 使用的 `ApiEnvelope` 增加状态优先解析器。
  非 0/200 业务码保留 code/msg/message，不解析成功 DTO，不使用拒绝响应中的 data。
  字段顺序不影响检查。成功或缺省业务码仍采用原来的严格 DTO 解析。
  成功响应格式异常时保留业务码和消息，不记录完整 data 或凭证。
- `requireData()` 先检查业务码，非空 data 也不能将拒绝响应变成成功。
- 开水各步骤保留失败上下文；格式不匹配提供可读原因和原始错误。
  登录失效和协程取消保持原异常，不包装成开水业务失败。
- APK 版本更新为 2.0.2 / 13，沿用原签名。

没有更改接口地址、请求头、签名、积分/实名/位置风控、支付或广告验证逻辑。
预检的普通失败仍按既有逻辑记录，不在本轮改变设备启动语义。

## 验证边界

测试通过 OkHttp 拦截器直接返回本地 JSON，不访问真实开水或支付接口。
覆盖正常 SKU 数组、拒绝响应 data={}、字段顺序、非空拒绝数据、
登录失效、未知成功对象、步骤诊断和取消传播。
这修复客户端误报，并不保证服务器批准启动；真实拒绝应按展示的业务原因处理。
